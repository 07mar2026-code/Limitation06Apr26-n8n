## 固定工作規則

每個功能都必須先建立可觀察、可判定成功／失敗的驗證節點。驗證輸出至少包含：

- 功能名稱
- 測試輸入
- 預期結果
- 實際結果
- PASS／FAIL
- 驗證時間

只有驗證全部通過才可更新為完成並在本機建立 Git 提交。正式發布必須執行 `scripts/publish-verified.sh`，通過遠端同步與資安硬性閘門後才可推送 GitHub。任何憑證、明文 token、個資或敏感測試內容不得進入 Git。

正式採用「本機 Git 為唯一提交來源」；不得使用 GitHub 網頁重複上傳已在本機提交的內容。完整規則見 [GitHub HTTPS 與正式發布規則](./GitHub-HTTPS與發布規則.md)。

## Webhook 與 OCR 呼叫鏈

- `Daily Shepherd` 為唯一 LINE production 入口。
- `Daily Shepherd` 的 `判斷 LINE 訊息類型` 包含 `OCR` 分支，圖片或檔案事件會進入 `F1. 呼叫 OCR 辨識服務`。
- `F1. 呼叫 OCR 辨識服務` 實際指向 OCR workflow 的唯一專用 path。
- OCR 的圖片與 PDF 辨識結果都進入 `回傳 OCR 辨識結果`，回傳給 Daily Shepherd。
- `F2. 回覆 LINE OCR 結果` 由 Daily Shepherd 統一呼叫 LINE reply endpoint。
- 主線節點不編碼；支線依功能使用 `A–H` 與執行順序編碼，兩條 workflow 合計 50 個節點名稱均唯一。
- 兩條 workflow 已於 2026-10-01 發布，線上匯出顯示 `active: true`。
